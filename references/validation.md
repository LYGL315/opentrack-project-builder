# OpenTrack 复跑验收与移交

## 设计对照场景

| 场景 | 控制变量与核验 |
| --- | --- |
| 正常基准 | 首跑先验证动力、连通、停点和终到。缺乏计划时刻时，可用无中间约束的试跑估计运行时间，并明确计划来源。建立完整计划后再跑一次，检查实际到发、停时和终到。 |
| 临时限速 | 与基准沿用同一计划、列车和径路。确认方向、作用边界、速度单位和起止时刻。比对区内的实际速度与边界位置，再比较逐车晚点。事件是否作用于某车，还要核对该车进路预留、实际到达与事件时窗。 |
| 多列车追踪 | 明确发车间隔与调度优先级。观察冲突股道上的预留、占用、释放，以及受影响列车的停车和再启动。需要比较停站或通过方案时只改目标车的停站方案，注明哪些计划时刻因此重算。 |
| 选做仿真事件 | 在基准副本启用单一模拟事件，例如虚构线路的临时限速或信号故障。核对事件启停、受影响对象、首车与后续列车及恢复过程。从同一计划和径路出发量化到达差、停车等待和占用。 |

设置与计划匹配的仿真时窗、日期偏移和计算步长，留足终到与必要释放时间。基准与变化组使用独立输出目录。保存每次有效运行的场景参数、输入差异和结果来源，避免拿到同名旧输出。

## 读原生输出

- 用 `OT_Timetable.txt` 或逐车 `.tt` 核对计划/实际到发、终到、通过和晚点。需要评估故障影响时，逐车比较同一事件前后的相同到发字段。
- 对照 `OT_Messages.txt` 的事件生效、停车、再启动和解除记录。计算停车等待时，以车次与信号为键匹配停车和再启动，区分零秒记录、缺失配对与正时长等待。检查信号信息缺失等告警；解释保留的告警及其影响。
- 用逐车 `.vs` 速度—距离和时间—距离输出，核对限速生效段、停车位置、恢复和列车顺序。用 `Corridor` / `Train Diagram` 查看全线时间—位置图，通过 `Plot` 打开相应原生结果；图上注明坐标单位和场景。
- 在包含 `SR`、`SO`、`EO`、`ER` 的股道占用输出中，`SR→ER` 是预留区间，`SO→EO` 是实际占用。先核对同一股道及车次是否有多次记录。统计股道合计占用时明确是逐车求和还是时间区间并集。
- 若要求报告，检查每张图都能追溯到本次仿真和对应原生记录。任务书要求原生图时，从 OpenTrack 实际导出，并保存绘图输入或原生图表工作表。

## Windows 旧版工程迁移

1. 打包全部相关工作表、数据库、运行文件和明确标注的基准输出。另存修改前的工程，检查底层对象引用是否随场景变化。迁移可先选择简短纯 ASCII 路径排除旧版路径或编码问题。
2. 检查 Preferences 与导出的 Run 文件中引用的库、基础设施工作表和输出目录。另查 Itinerary 库（常见 `.dest`）中的工作表绑定。文件名一致时也可能仍引用旧位置。通过本机支持的方法重存、重建或重新关联，以具备经验证格式支持的工具处理二进制档案。
3. 从新目录启动独立副本，确认引用解析到该副本，必要时在可安全隔离的环境中复跑，确保旧路径无法偶然满足依赖。某些 1.x 环境支持 `-scriptinit -runfile=<运行文件>`，按本机发行说明和实测确定。检查新输出的写入时间和预期车次完成情况。
4. 同一场景迁移前后，比较选定原生时刻表、代表列车轨迹与股道占用的数据行；对照日志中关键事件。比较工具只忽略明确允许忽略的元数据。先查差异原因，再决定是否属于版本变化或真实模型变化。

```powershell
python scripts/compare_outputs.py baseline rerun OT_Timetable.txt OT_T01.tt OT_T01.vs
```

脚本以指定顺序比较数据行，忽略空行、行尾空白以及以 `//` 起始的注释行。内部制表符及数据行顺序参与比较。默认 UTF-8，可用 `--encoding cp936` 等指定原生文件编码。结束码 `0` 为所选文件一致，`1` 为有数据行差异，`2` 为路径、读文件或编码错误。脚本不解释车次终到和业务合理性。

交付前用任务书逐项验收。证据至少指出场景、文件、行或车次，并附输入假设与未验证项。保存备份和版本变化记录。公开分享时，使用自己的通用方法、独立实现和虚构示例，遵循来源和软件的授权范围。
